# Safety, Security and Simulation Limitations — v0.9.2

## Intended use

OmniFleet AI is a software-only portfolio/interview prototype for multi-agent fleet orchestration. It is not a flight controller, mission-critical command system, sensor platform or deployable autonomy stack.

## No hardware control path

The current application binds its active dispatch adapter to `SimulatedVehicleAdapter`. The method-level adapter seam is not a production hardware-driver framework. `PX4SITLAdapter` exists as a deliberately non-operational placeholder and is not wired into the active application.

- `SimulatedVehicleAdapter` mutates local Python simulation objects only.
- `PX4SITLAdapter` is a placeholder that refuses dispatch.
- No MAVLink, MAVSDK, PX4, ROS 2, DDS, MQTT, camera, physical radio or physical vehicle connection is created.
- Approval, tasking, radio toggles and map interactions operate only on the local simulation.

## Geospatial boundaries and route planning

The WGS84 display uses a small-area equirectangular approximation around an illustrative Bengaluru origin. It is not navigation-grade. The operating geofence, restricted polygon and fixed virtual structure are illustrative test geometry, not surveyed boundaries or legal airspace. The deterministic planner checks route segments against these shapes and the current moving-obstacle polygon. The moving obstacle follows a bounded, scripted lane; it is not sensed from an environment. Route checks use finite spatial sampling and do not constitute formal geometric proofs. No terrain, vertical clearance, altitude-dependent obstacles or real perception is modeled.

## Vehicle dynamics and separation

Speed and acceleration use SI units and are converted to local map displacement using the theatre scale. Motion remains simplified 2-D kinematics. The simulator performs synchronized closest-approach checks, deterministic right-of-way, boundary clipping and lateral detours. If a path cannot be made safe, vehicles wait and ultimately enter a safe hold; the mission monitor marks incomplete tasks degraded. The 2-local-unit separation radius is a demo parameter (40 m in the default theatre), not an aircraft separation standard. This is not a validated collision-avoidance controller or continuous-time trajectory planner. Wind, inertia, rotor/wing dynamics, vertical manoeuvres, terrain, weather and validated vehicle dynamics are absent.

## Battery and recovery

Battery drain is illustrative, not calibrated to a real platform. Below 20%, the system estimates the return-home energy requirement using route length, configured acceleration/speed, a 30% contingency and a protected 5% reserve. If return is not feasible, an aircraft may receive an emergency local-land proposal and a ground vehicle a safe-hold proposal, provided the current location passes demo safety checks. If no safe local recovery exists, the system reports `RECOVERY_UNAVAILABLE`. Approval is always required. A recovery proposal can pre-empt an executing simulated task, which is marked degraded.

## Coverage planning

Area coverage uses a deterministic sweep planner for convex polygons, with safe transit routing to the first lane and around the currently modeled obstacle geometry. It is not an optimal coverage algorithm and does not prove collision-free execution or regulatory compliance. The generic `area_coverage` capability is demo metadata; it does not imply real aerial/ground platform interchangeability.

## Sensor simulation

Sensor footprints are isotropic circles. Observations are generated by geometric range checks against operator-placed virtual objects. There is no camera feed, computer vision, image recognition, target identity verification, occlusion, altitude geometry or calibrated uncertainty model. Confidence is a deterministic demo score. `CORROBORATED` means multiple simulated sources observed the same object revision; it is not proof of identity or authenticity.

## Communications simulation

The swarm layer is an in-process deterministic message bus. Direct peer messages require both vehicles to be within the smaller configured communication radius. Fleet knowledge is recipient-specific and changes only when a heartbeat is delivered; disconnected peers retain stale last-known state. Configurable latency (0–10 simulation ticks) queues messages, and packet loss (0–100%) is applied deterministically from message metadata. Delayed task negotiation waits for delivery and retries a bounded number of times. These are reproducible test controls, not RF propagation or realistic stochastic network behavior. Bandwidth, terrain/antenna effects, interference, authentication, encryption, QoS, multi-hop routing and distributed consensus are not modeled.

## Approval and authority

Mission actions, map waypoints, inspection proposals and recovery proposals require explicit operator approval. The backend revalidates constraints immediately before dispatch. If any action in a multi-vehicle mission violates policy, the complete mission proposal is rejected atomically. This approval gate is a demo control, not a complete safety assurance case. Never treat an LLM response or simulator result as an authoritative real-world instruction.

## Security limitations

The local demo has no login, roles, CSRF protection, rate limiting, hardened secrets management or production audit integrity. Run it on localhost only. Do not expose it to a public or untrusted network. Store API credentials only in `.env`, keep `.env` out of source control, and rotate any key that is accidentally exposed.

## Prohibited interpretation

Do not use this software for flight testing, navigation, real surveillance, safety-critical decisions, airspace authorization, physical vehicle control or operational tasking. Any real-world integration requires a separate engineering programme, hazard analysis, security review, regulatory compliance work, validated vehicle and sensor models, hardware-in-the-loop testing and qualified human oversight.
